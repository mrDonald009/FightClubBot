# Эталонная модель БД для клубного Telegram-бота

Документ задаёт **правила проектирования** для FightClubBot и будущих клонов (другие клубы, другие инстансы).  
Это **операционная OLTP-модель** (бот пишет и читает каждый день), не хранилище для BI.

**Связанные материалы (детали реализации):**

| Документ | Содержание |
|----------|------------|
| `database/schema_diagram.md` | ER-диаграмма текущей схемы |
| `ARCHITECTURE_DESCRIPTION.md` | Процессы, заморозки, несколько абонементов |
| `doc/ARCHITECTURE.md` | Слои кода, `db_utils`, env |

## 1. Два слоя данных

| Слой | Назначение | Когда вводить |
|------|------------|---------------|
| **OLTP** (этот документ) | Карточки, абонементы, посещения, заморозки | Всегда, с первого бота |
| **Аналитика** (звезда / снежинка) | Отчёты, дашборды, «посещений по тренерам за месяц» | Отдельная БД или ETL, когда появится реальная потребность |

Не перестраивать операционную SQLite «вокруг одной таблицы фактов» — для бота это усложнит транзакции без выгоды.

---

## 2. Центр модели

**Стабильный идентификатор человека в клубе — `athletes.id` (member id).**

Все учётные связи идут через него или через производные id:

```
athletes.id
    ├── subscriptions (athlete_id)
    │       ├── attendances (subscription_id)
    │       ├── subscription_payments
    │       └── global_freeze_applications
    ├── athlete_freezes
    └── visit_history (через attendance / athlete_id)
```

### Не являются ключами связей

| Поле | Роль |
|------|------|
| `phone` | Контакт, уникальность при вводе; **не** поиск «чужого» абонемента |
| `telegram_id` (спортсмена) | Опциональная привязка к Telegram; может быть NULL |
| `full_name` | Отображение; не уникальность в БД |

**Правило:** изменение телефона, ФИО или Telegram **не переносит** абонементы и историю на другого человека — меняется только атрибут у того же `athlete_id`.

## 3. Блоки сущностей (эталон клуба)

### 3.1 Identity — кто в системе

| Сущность | Таблица (FightClubBot) | Заметки |
|----------|------------------------|---------|
| Спортсмен | `athletes` | Ядро домена |
| Тренер | `coaches` | `telegram_id`, вид спорта |
| Админ / ассистент | `admins`, `assistants` | Роли staff |
| Staff в процессе | `.env` + строки в `coaches`/`admins` | ID из env — **поведение при старте**; факт роли — в SQLite |

### 3.2 Catalog — справочники и настройки

| Сущность | Таблица | Заметки |
|----------|---------|---------|
| Вид спорта | `sport_types` | Предпочитать `sport_type_id` |
| Тариф / цена | `subscription_tariffs` | Цены активации **только** отсюда |
| Настройки клуба | `club_settings` | Длительность слота и т.п., не `.env` |

Строковый `sport_type` на старых строках — **legacy**; новый код пишет `sport_type_id` где возможно.

### 3.3 Contract — договор / абонемент

| Сущность | Таблица | Заметки |
|----------|---------|---------|
| Абонемент | `subscriptions` | Ключ направления: `discipline_key` |
| Оплата | `subscription_payments` | Выручка, аудит сумм |

Один активный абонемент на пару **`(athlete_id, discipline_key)`** (групповые/месячные/разовые).  
Индивидуальные слоты — отдельные правила уникальности по `start_date` (см. модели).

Выбор абонемента в логике: **`utils/subscription_resolve.py`**, не «первый активный» из свойства athlete.

### 3.4 Activity — факты занятий

| Сущность | Таблица | Заметки |
|----------|---------|---------|
| Слот тренировки | `trainings` | Расписание + слоты в БД |
| Посещение / списание | `attendances` | Всегда с `subscription_id` |
| История для UI | `visit_history` | Синхронизировать с attendance единым путём (`visit_history.upsert_visit_history_for_training`) |

### 3.5 Policy — заморозки и исключения

| Уровень | Таблица / поля |
|---------|----------------|
| Абонемент | `subscriptions.is_frozen`, даты, продление `end_date` |
| Спортсмен целиком | `athlete_freezes` |
| Клуб (массовая) | `global_freezes`, `global_freeze_applications` |

### 3.6 Audit (по необходимости)

| Что | Где сейчас |
|-----|------------|
| Оплаты | `subscription_payments` |
| Заморозки спортсмена | `athlete_freezes` |
| Изменения полей карточки | пока только в UI; при необходимости — отдельная `athlete_field_audit` |

## 4. Правила для новой логики (чеклист)

Перед merge любой фичи:

1. **К какому id привязана запись?** (`athlete_id`, `subscription_id`, `training_id`)
2. **Ищем ли человека по phone / ФИО / telegram для связи?** → должно быть **нет** (допустима только проверка дубликата при вводе)
3. **Справочник или цена** — в таблице catalog, не в коде и не в `.env`
4. **Несколько активных абонементов** — явный выбор через `subscription_resolve`, не `athlete.current_subscription`
5. **Запись посещения** — `attendance` + при необходимости `visit_history` одним upsert-путём
6. **Handlers** — тонкий слой; бизнес-логика в `services/` или `database/db_utils/`

---

## 5. Запреты (антипаттерны)

- Использовать **телефон** как внешний ключ к абонементам или посещениям
- При смене контакта **объединять** двух спортсменов или **перепривязывать** чужие `subscription_id`
- Хранить **цены активации** в переменных окружения
- Дублировать расчёт остатка тренировок в handler без `sync_subscription_trainings_remaining` / `remaining.py`
- Добавлять отчётную «таблицу фактов» в ту же БД, что и бот, без отдельного процесса ETL

## 6. Несколько клубов в будущем

Два допустимых пути (выбрать явно при втором клубе):

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **Отдельный инстанс** (бот + `.env` + SQLite на клуб) | Изоляция, как сейчас dev/prod | N деплоев |
| **Multi-tenant** (`club_id` во всех таблицах) | Один процесс | Миграция, риск утечки данных между клубами |

**Рекомендация на текущий масштаб:** отдельный инстанс на клуб; `club_id` вводить, когда появится один код и одна БД на несколько залов.

## 7. План эволюции схемы (FightClubBot)

Приоритет без ломки продакшена:

1. **UNIQUE** на `athletes.phone` (WHERE phone IS NOT NULL) — дубли только в коде сейчас
2. Запись **`sport_type_id`** при создании athlete/subscription/training (строка — read-only legacy)
3. Индексы и UNIQUE по тарифам — по мере узких мест
4. Аналитический слой — только при запросе отчётности
